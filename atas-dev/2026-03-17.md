# 📋 Ata de Reunião – Modelagem e Direcionamento do Sistema de Bingo
Data: 2026-03-17

## 1. 🧭 Contexto da Reunião

Esta reunião teve como objetivo definir a arquitetura correta do sistema de bingo, com foco em:

- consistência de dados
- performance
- integridade de regras de negócio
- preparação para escalabilidade

Nenhuma implementação foi realizada neste momento — apenas decisões técnicas e direcionamento estratégico.

## 2. ❗ Problemas Identificados (Durante Discussão)

### 2.1 Modelagem anterior inadequada

- Uso de colunas `n1...n24` para cartelas
- Estrutura rígida e difícil de manter
- Alto acoplamento com regras de negócio

### 2.2 Falta de garantia de unicidade

- Possibilidade de cartelas duplicadas no mesmo sorteio
- Falta de constraint eficiente para evitar duplicidade

### 2.3 Dúvida sobre performance

- Comparação direta de JSON considerada ineficiente
- Avaliação de uso de bitmask para otimização

### 2.4 Problema de concorrência

- Risco de disputa por:
- "quem ganhou primeiro?"

### 2.5 Modelagem incorreta do sorteio

- Estrutura fixa (`n1...n24`) não representa o comportamento real do bingo
- Sorteio é dinâmico e progressivo

## 3. ❌ Alternativas Rejeitadas

### 3.1 Uso de Bitmask

Motivo:

- Limitação de 64 bits no banco
- Necessidade de soluções complexas (multi-coluna / binário customizado)
- Aumento de complexidade desnecessária nesta fase

👉 Decisão:
Não utilizar bitmask neste momento

### 3.2 Comparação direta de JSON

Motivo:

- Baixa performance
- Dificuldade de indexação
- Complexidade em queries

## 4. ✅ Decisões Arquiteturais

### 4.1 Estrutura das Cartelas

Utilizar campo:

`numeros` (JSON)

- Representa os 24 números da cartela

### 4.2 Garantia de Unicidade

Criar campo:

`hash` (SHA-256)

- Baseado no JSON ordenado

Constraint:

`UNIQUE (sorteio_id, hash)`

### 4.3 Estrutura do Sorteio

Campo:

`numeros_sorteados` (JSON)

- Representa a ordem real do sorteio

### 4.4 Regra de Vitória

`cartela ⊆ sorteio`

👉 Interpretação:

- Todos os números da cartela devem estar contidos no sorteio
- Ordem NÃO importa para validação

### 4.5 Regra de Premiação

- Múltiplos vencedores são permitidos
- Prêmio deve ser dividido igualmente

## 5. 🧠 Regras de Negócio Definidas

- Paróquia é a entidade raiz do sistema
- Usuários pertencem a uma paróquia
- Cartelas pertencem a um usuário
- Sorteios pertencem a uma paróquia
- Cartelas pertencem a um sorteio

## 6. 🗄️ Banco de Dados

### 6.1 Tabela: usuarios

- `paroquia_id` → `NOT NULL` (obrigatório)

### 6.2 Tabela: cartelas

Campos obrigatórios:

- `usuario_id`
- `sorteio_id`
- `numeros` (JSON)
- `hash`

Constraint:

`UNIQUE (sorteio_id, hash)`

### 6.3 Tabela: sorteios

Campos:

- `paroquia_id`
- `numeros_sorteados` (JSON)
- `cartela_vencedora_id` (UNIQUE, opcional)

## 7. ⚙️ Backend (FastAPI)

### 7.1 Validação de Cartelas

- 24 números obrigatórios
- valores entre 1 e 75
- sem repetição
- ordenados antes de gerar hash

### 7.2 Validação de Sorteio

- números entre 1 e 75
- sem repetição
- manter ordem original (não ordenar)

### 7.3 Geração de Hash

- Baseado no JSON ordenado
- algoritmo: SHA-256

### 7.4 Verificação de Vencedores

- Converter lista para set
- Verificar:

`set(cartela).issubset(set(sorteio))`

## 8. 🎨 Frontend

### 8.1 Criação de Cartelas

- Ordenar números antes de enviar
- Garantir ausência de duplicados

### 8.2 Comunicação com Backend

- Enviar apenas JSON
- Não enviar hash

## 9. ⚠️ Decisões Importantes de Arquitetura

- JSON é a fonte de verdade
- Hash é apenas mecanismo de:
- unicidade
- performance
- Não usar estrutura fixa (`n1...n24`)
- Não usar bitmask nesta fase

## 10. 📌 Pontos de Atenção (Identificados para Implementação)

- Garantir integridade referencial no banco
- Garantir validações no backend (não confiar só no frontend)
- Evitar duplicidade de cartelas
- Preservar ordem do sorteio
- Separar claramente:
- dados estruturais
- regras de negócio
